# Data Quality and Table Constraints in DLT

## Table Lifecycle in Lakeflow (Delta Live Tables)
All tables across the Bronze, Silver, and Gold layers are dynamically generated by the declarative Delta Live Tables (Lakeflow) pipeline. Each dataset is defined as either a **Streaming Table** or a **Materialized View**.

## Constraints Management in DLT
DLT manages schema and table lifecycle automatically, which means:

- Manual `ALTER TABLE ... ADD CONSTRAINT` commands are **not supported**.
- Attempts to apply standard Delta constraints via SQL will result in runtime errors, such as:
  - `EXPECT_TABLE_NOT_VIEW`
  - `STREAMING_TABLE_OPERATION_NOT_ALLOWED`

## Enforcing Table-Level Expectations

DLT uses native Lakeflow expectations with fail-fast policies to enforce data quality:

- `@dp.expect_all_or_fail`
- `@dp.expect_or_fail`

### NOT NULL Enforcement

- Key columns (e.g., `video_id`, `author`, and `_ingested_at`) are validated against null or blank values.

### CHECK Constraints

- Logical conditions, such as:
  - `view_count >= 0`
  - `length(video_id) = 11`
- Ensure invalid metrics or broken identifiers are rejected.

### Write Rejection

If any incoming record fails these expectations:
- DLT immediately stops pipeline execution and fails the run.
- Prevents bad data from being committed to storage.

---

**Summary:**  
This approach achieves the same safety guarantees as traditional table constraints while remaining fully compatible with declarative DLT pipelines.
